## 本会话模型与上下文窗口（SOP 第一条）

本 session 跑 `claude-opus-5`，上下文窗口 **1,000,000**，是 SOP 要求的 200K 上限的
5 倍。按 SOP 的要求自报偏差后继续，自己在每个 cap 边界读上下文：峰值 233,994，是在
cap6/cap7 之后才越过 200K 的，那时剩下的只有读回和写报告，再切一个 session 的开销
会大于省下的钱，所以没有切。上一个 session 同样是 1M 窗口，峰值 242,766。

**这条规则需要重新表述。**「超过 200K 就切 session」在 cap 边界上是可执行的，但一个
cap 组本身就要烧掉 20 万上下文，所以真正发生的是：每个 session 都在接近 200K 的地方
结束，而不是在 200K 处被切开。规则实际起的作用是「一个 cap 组一个 session」，上限
数字只是事后确认。

## 过程中觉得冗余或 SOP 没说清的地方

1. **第 175 题的分栏被 assemble 压扁后，cap4 再也修不回来。**
   忠实层 `lines` 本来保留了「3 栏 × 2 行」的印刷结构，但 `text` 把它们无分隔地拼成
   一行，产生了 `1分20秒3 500厘米` 这样的连写。想在现代版里把行恢复出来时，
   `3 500厘米` 跑到了行首——`edition.py` 的 `NUMBER` 正则是
   `(?<![\w.])-?\d+(?:\.\d+)?(?![\w.])`，而 Python 的 `\w` 包含汉字，所以紧贴汉字的
   数字在 signature 里根本不出现；一换行，`3` 突然"冒出来"，直接报
   `非公式数字变化未被准确声明: want=[], got=['3']`。结果是**发布出去的第 175 题仍然
   带着这个连写**。根因在 assemble 拼行不加分隔符，但 cap4 的数字守卫把它锁死了，
   值得单开一张工单。
2. **`grid` 语义色在「格线本身有意义」时太淡。**
   `tbl-p0043-01` 里 A–O–K 这条底边就是一条格线，三角形 ABO、ABK 全靠它闭合。用
   `grid` 角色（`#e3eae9`）渲出来格线几乎看不见，图就废了，只能改用 `muted`。
   `figure-generation.md` 和 `figure-spec.md` 都没提这件事。
3. **格点上的标签不能用正方向放置。**
   `S`/`N`/`E`/`W` 会把标签摆在锚点的轴线上，而格点恰好坐在格线上，必然触发
   `strokeCollision`（+10000 分）直接 fail。点在格子交点上时只有四个斜向可用。
   这条没写在任何地方，白花了一轮渲染。
4. **`height ≥ 320` 加上 `keepAspectRatio` 等于禁止"宽而扁"的图。**
   原书两张表是左右并排的，长宽比约 22.5 : 6.1，照抄的话 height 只能是 173，过不了
   schema。只能改成上下堆叠（已在 spec description 里声明为现代版重排）。契约要么
   明说"宽表格一律重排"，要么对 `layout: "scroll"` 放宽这个下限。
5. **SOP 与派工单的次序不一致。** SOP 第 3、4 条是「先 commit+push，再写库，发布的
   是已 push 的快照」；派工单把 commit/push 放在 cap6/cap7 之后的收尾里。本次按 SOP
   执行（先 push `c89c71d06` 再 publish）。派工模板应该跟 SOP 对齐。
6. **`publish.mjs --dry` 会把整册的重排清单（约 500 行）打一遍，真跑时再打一遍。**
   在一个按 token 计费的 session 里这是纯噪音，建议加 `--quiet` 或只打受影响的课。
7. **`meter.py` 的 800 万预算对一整课没有信息量。** 两个 session 都是 2800 万，是预算
   的 3.5 倍；也就是说这个信号在真正开始干活之前就已经触发了。要么调高，要么改成
   按 cap 计。
