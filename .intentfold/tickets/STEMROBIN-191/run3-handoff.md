### 两条必须说清楚的话

**第一，200K 这条线两个 session 都没守住。** session 1 在 cap3/cap4 边界已经是
233,441 才交接，session 2 在 cap4 `adapt-finalize` 刚跑完就到 200,748，之后 cap5、
cap6、cap7、收尾一路走到 235K，没有再切。也就是说这次实验里「接近 200K 就交接」
这条规则**只被执行了一次**（session 1 → session 2），而那一次也是事后越线交接，不是
踩线交接。按改写后的规则，session 2 应该在 cap4 结束、200,748 那一刻就把 cap5–cap7
交给第三个 session。我没有这么做——当时判断剩下的只有四条命令加一次读回，而一个新
session 光是读 SOP + SKILL.md + reference 开场就要 8.5 万上下文，换算下来交接比不交接
更贵。**这是对规则的偏离，不是对规则的验证**，记在这里由工单主人裁决。

**第二，session 2 这张表是事后从 transcript 重建的，不是当场读的。** 每个 assistant
turn 的 `usage` 里 `input + cache_read + cache_creation` 就是那一轮的真实上下文，按
cap 的锚点命令对齐即可复原，数字是真的；但「在每个 cap 边界读一次」这个动作我当时
没做——SOP 改写后的那段确实写了「Record the per-cap context readings」，我读了那个
文件却漏了这一句。session 1 则是当场读了两次（开场、cap3/cap4 边界），中间 cap1、
cap2、cap3 是连着一串命令跑完的，没有单独读数。

### 这条规则本身需要重新表述

「超过 200K 就切 session」在 cap 边界上是可执行的，但**一个 cap 组本身就要烧掉 10–14
万上下文**（session 2 从 85,665 走到 221,916，净增 13.6 万；session 1 从 90,668 走到
251,808，净增 16.1 万），而每个新 session 的开场固定成本是 8.5–9 万。两者相加就超过
200K——所以真正会发生的永远是「每个 session 在 22–25 万处结束」，而不是「在 200K 处
被切开」。规则实际起的作用是「一个 cap 组一个 session」，200K 这个数字在当前的 SOP
体积下是达不到的。要让上限真正有意义，得先把开场的固定上下文（SOP + SKILL.md +
两份 reference，约 8.5 万）压下来。

## 过程中觉得冗余或 SOP 没说清的地方

1. **第 175 题的分栏被 assemble 压扁后，cap4 再也修不回来。**
   忠实层 `lines` 本来保留了「3 栏 × 2 行」的印刷结构，但 `text` 把它们无分隔地拼成
   一行，产生了 `1分20秒3 500厘米` 这样的连写。想在现代版里把行恢复出来时，
   `3 500厘米` 跑到了行首——`edition.py` 的 `NUMBER` 正则是
   `(?<![\w.])-?\d+(?:\.\d+)?(?![\w.])`，而 Python 的 `\w` 包含汉字，所以紧贴汉字的
   数字在 signature 里根本不出现；一换行，`3` 突然"冒出来"，直接报
   `非公式数字变化未被准确声明: want=[], got=['3']`。结果是**发布出去的第 175 题仍然
   带着这个连写**。根因在 assemble 拼行不加分隔符，但 cap4 的数字守卫把它锁死了，
   值得单开一张工单。
2. **`grid` 语义色在「格线本身有意义」时太淡。**
   `tbl-p0043-01` 里 A–O–K 这条底边就是一条格线，三角形 ABO、ABK 全靠它闭合。用
   `grid` 角色（`#e3eae9`）渲出来格线几乎看不见，图就废了，只能改用 `muted`。
   `figure-generation.md` 和 `figure-spec.md` 都没提这件事。
3. **格点上的标签不能用正方向放置。**
   `S`/`N`/`E`/`W` 会把标签摆在锚点的轴线上，而格点恰好坐在格线上，必然触发
   `strokeCollision`（+10000 分）直接 fail。点在格子交点上时只有四个斜向可用。
   这条没写在任何地方，白花了一轮渲染。
4. **`height ≥ 320` 加上 `keepAspectRatio` 等于禁止"宽而扁"的图。**
   原书两张表是左右并排的，长宽比约 22.5 : 6.1，照抄的话 height 只能是 173，过不了
   schema。只能改成上下堆叠（已在 spec description 里声明为现代版重排）。契约要么
   明说"宽表格一律重排"，要么对 `layout: "scroll"` 放宽这个下限。
5. **SOP 与派工单的次序不一致。** SOP 第 3、4 条是「先 commit+push，再写库，发布的
   是已 push 的快照」；派工单把 commit/push 放在 cap6/cap7 之后的收尾里。本次按 SOP
   执行（先 push `c89c71d06` 再 publish）。派工模板应该跟 SOP 对齐。
6. **`publish.mjs --dry` 会把整册的重排清单（约 500 行）打一遍，真跑时再打一遍。**
   在一个按 token 计费的 session 里这是纯噪音，建议加 `--quiet` 或只打受影响的课。
7. **`meter.py` 的 800 万预算对一整课没有信息量。** 两个 session 都是 2800 万，是预算
   的 3.5 倍；也就是说这个信号在真正开始干活之前就已经触发了。要么调高，要么改成
   按 cap 计。
