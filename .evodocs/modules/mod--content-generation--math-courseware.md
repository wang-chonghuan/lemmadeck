# purpose

The math-courseware module turns scanned Soviet ten-year-school mathematics textbooks into modern LemmaDeck cards. Its sole entry for creating a new math lesson is `ld-s10y-lesson`. That workflow locates a numbered unit through the repository TOC, transcribes scan pages into typed source objects, assembles cross-page lessons and exercises, creates a culturally modern edition, delegates product figures to `ld-s10y-image`, publishes the base lesson to `sr_lessons`, and then delegates answer keys and interaction specifications to `ld-s10y-answer`.

The module preserves two truths at once. The raw extraction layer records what the printed book contains, including its numbering, formulas, page provenance, figures, and even apparent source defects. The edition layer is the only place where cultural context, names, units, layout, and product figures may be modernized. This separation allows a later agent to audit a modern card against the scan without treating the scan itself as learner-facing content.

The published unit is a textbook card, not a generated whole-page document and not a concept-led card tree. One TOC card id maps to one `sr_lessons` row whose `content.prose` and `exercises.exercises` contain host-embeddable HTML fragments and inline figure data. Answers and interaction metadata are added to those same exercise objects after the lesson exists. The application renders the result at `/card/:id` using its own typography and keeps all expected answers server-side.

# structure

The persistent lesson model lives under `ssot-resources/soviet10year-textbooks/artifacts/<book>`. Page directories keep typed `page.md` blocks, normalized JSON and page audits. Rendered scan images, coordinate grids, templates and page-level figure crops live under `.tmp/ld-s10y-lesson/<book>/`; they are rebuildable intermediates. The book-level raw layer keeps the promoted figure library, assembled lesson directories, independent exercise arrays and a `book.json` audit. This layer remains a faithful extraction source and is never edited to perform modernization.

A page transcription is an ordered sequence of typed blocks. Headings establish chapter, section, and unit boundaries; prose, exercise headers, exercises, figures, captions, and footers preserve object roles. Continuation flags express an object split across a page or interrupted by a figure. A shared-row flag preserves printed line accounting, and an explicit exercise owner is required for an unnumbered table or diagram that cannot be referenced by a printed figure number. The model identifies semantic objects and supplies approximate boxes; deterministic code owns coordinates, cropping, normalization, and reconciliation.

Assembly converts page blocks into publishable units. It merges compatible cross-page fragments, starts a unit at each third-level heading, separates exercises from prose, and assigns figures by semantic references. Every exercise that references a shared figure keeps the reference, but only the nearest referring exercise owns the display instance. A figure used only by exercises is removed from prose; a figure genuinely referenced by both prose and exercises appears once in each relevant context. The TOC assigns the stable card id only when the printed unit number and starting printed page agree.

The edition layer lives under `editions/<edition>`. Preparation copies complete raw lesson and exercise snapshots, with hashes and source data, into editable lesson, exercise, and figure templates. Modern text retains source text, declared change categories, and an explicit list of non-formula number changes. Finalization requires unchanged lesson identity, exercise count and order, figure ids and order, and mathematical-expression signatures. It also normalizes complete numbered subparts into ascending order with one subpart per line and enforces the selected profile's cultural restrictions.

Modern figures are a delegated subdomain. `ld-s10y-image` builds a context package from every edition lesson and exercise that references the figure, plus the original PNG and its hash. Its canonical `ld-s10y-image/figure-spec@1` contract describes source evidence, authoritative edition text, a canvas and mathematical coordinate space, ordered render objects, machine-checkable assertions, assets, layout exclusions, and human review. Exact geometry is rendered by JSXGraph, semantic scenes are generated through Azure `gpt-image-2`, and hybrid figures put generated artwork below a deterministic mathematical overlay.

Answers form a separate downstream layer. Book-level `answers.json` is a faithful capture of printed answer pages and remains evidence only. Edition-level `answer-keys.json` contains one solved answer per exercise, with a learner-facing standard answer and either auto-gradable parts or an explicit ungraded classification. `interactions.json` then describes how the learner should answer without carrying the answer itself. The lesson, answer, and interaction publishers each own a distinct merge into the same `sr_lessons.exercises` JSONB document.

# flows

Production begins by locating a unique book and TOC unit. The TOC provides the card id, printed unit number, title, and page range; the scan provides the actual content. Page preparation renders one physical PDF page at high resolution and adds a coordinate grid. The authoring model reads one page at a time and writes typed blocks, using neighboring text rather than lowering image resolution when cross-page context is needed.

Page finalization turns that visual interpretation into checked source data. Approximate figure boxes are snapped to connected ink components before cropping into `.tmp/`. Overlapping boxes fail. After figure regions are removed, the detected printed rows must equal the rows represented by the transcribed blocks. Text is normalized only at the encoding level, such as full-width digits, Unicode scripts, fraction macros, and minus signs inside math. Character allowlists, Cyrillic enumeration markers, printed-page provenance, delimiter balance, and KaTeX parsing are checked. Incomplete cross-page formulas may defer their final check only when the block is explicitly marked as continued.

Assembly processes all finalized pages in source order. Open and continuation blocks are joined across transparent figure, caption, and footer interruptions. Exercise and figure numbering are audited across the assembled range, formulas are rechecked after joining, shared figures are de-duplicated, and exercise-only graphics are prevented from leaking into prose. TOC coverage gaps and identity mismatches remain visible. Without a TOC-derived card id, a requested lesson cannot pass publication.

Raw page-level figures may be traced into SVG with potrace while still under `.tmp/`. The SVG is rerasterized with resvg and compared against the source ink; more than two percent mismatch after a one-pixel edge tolerance fails. This trace is not a modern product illustration. After vectorization, assembly promotes the final PNG/SVG pair into the persistent book-level figure library without clearing figures from earlier runs.

Edition preparation freezes the raw lesson and exercise inputs. Modernization may change cultural setting, names, units, and non-mathematical context, but it may not change the mathematical objective, formula sequence, exercise identity, grouping, figure references, or quantity of material. Formula signatures must remain exact. Every non-formula number change must declare the original value, replacement, and reason, and the change list must identify it as a context-number change. The modern profile also rejects Cyrillic text and named Soviet cultural remnants.

Every modern figure is routed through `ld-s10y-image`. Deterministic mode is required for points, lines, axes, ticks, grids, measurements, coordinates, transformations, charts, mathematical labels, and other exact relations. Generated mode is limited to semantic identity or scene content that does not depend on exact placement. Hybrid mode combines natural artwork with deterministic geometry. The edition text is authoritative, while the original PNG supplies composition and visual evidence; answer keys are forbidden as figure inputs.

Figure validation occurs at both semantic and rendered levels. The FigureSpec validator resolves point references and checks declared distances, equal distances, collinearity, parallelism, perpendicularity, points on lines, object counts, and central-symmetry pairs. Generated specs cannot contain deterministic objects, deterministic specs cannot contain images, and hybrid images must precede their overlays. Visible labels must be English. The JSXGraph renderer preserves hybrid image aspect ratios, calculates label placements against points, artwork regions, existing labels, canvas bounds, and geometry, and emits a hash-bound report. Any failed assertion, collision, clipping-related placement, missing asset, stale hash, or failed human review blocks edition finalization.

After edition finalization passes, offline rendering creates self-contained text and exercise pages for visual inspection. Production publication does not store those whole documents. Instead, the lesson publisher converts each text block and exercise prompt into a KaTeX-rendered HTML fragment, embeds approved SVG or PNG figures, and upserts the card into `sr_lessons`. It writes `content.prose` and `exercises.exercises`, sets `html` to null on update, and preserves existing answer keys by exercise number when republishing the same edition. It does not preserve existing interaction metadata, so the interaction publisher must run again after a base lesson is republished.

Answer production follows the published edition. Printed answer pages may first be captured as raw evidence. Answer preparation then reads the modern prompts and figure manifest, attaches any printed answer as `bookRaw`, and gives the solver paths to the original PNG, modern asset, and FigureSpec. Every exercise must receive a correct `displayAnswer`. Reliably judgeable work is split into `exact`, `numeric`, or `expression` parts; drawings, proofs, and open reasoning remain `ungraded` but still provide a standard answer. A semantic gate checks the actual mathematics before finalization.

The answer publisher requires a ready answer document, a passing audit, an existing lesson row, the same edition, and exact exercise coverage. It updates all selected lessons transactionally by adding `answerKey` beside each stored exercise. Interaction generation then derives public input shape from those answer keys. Ungraded work becomes `free`; expressions use `math`; plain numeric parts use `number` unless they can be proven to be a coordinate-grid interaction. Exact or mixed answers currently remain `math` with an explicit `needsAuthoring` marker when a choice interaction has not been defined.

For `grid-point`, the interaction tool reconstructs a coordinate frame and named points from a deterministic FigureSpec. It accepts the result only when the number and order of answer parts match x/y coordinates for every named point and each expected value equals the corresponding coordinate. For `grid-plot`, the target coordinates are read from the prompt and checked against the answer parts in the same ordered way. Final validation recomputes these derivations. The interaction publisher then adds only widget shape, grid domain, point names, and part mappings; expected values and display answers remain solely in `answerKey`.

# module-relationships

The repository TOC is upstream identity and navigation authority. It determines which printed unit becomes which application card, and the application uses the same ids to build the catalog, breadcrumbs, and previous/next navigation. A content row with an invented id or no TOC match is unreachable even if its prose is otherwise valid.

The scan corpus is the other upstream authority. Page images, printed numbers, and original figures define what was extracted. The modern profile governs allowed adaptation but does not supersede the source mathematics. Raw artifacts and hashes provide the evidence needed to detect stale editions after a re-extraction.

Within content generation, `ld-s10y-lesson` is the coordinator and only new-lesson entry. `ld-s10y-image` is a required delegate for modern figures rather than an alternate lesson generator. `ld-s10y-answer` is downstream of a finalized edition because answers must follow modern names, units, prompts, and figures. Figure production must never depend on answers, while answer production may and often must inspect figures.

The database-schema module supplies the persistent `sr_lessons` JSONB contract. The lesson publisher owns the base content and exercise shape, the answer publisher owns `answerKey`, and the interaction publisher owns `interaction`. Each later publisher preserves fields written by the earlier stages. `sr_content_answer_events` and `sr_textbook_mistakes` are downstream learner-state tables written by server-side answer checking, not by generation.

The application domain layer consumes the new S10Y shape through `app/src/lib/lessons.ts` and `_app/card.$id.tsx`. Availability means that a row has at least one prose block or a positive exercise count. The browser receives rendered prose, figures, prompts, grading shape, labels, units, and answer widgets. It does not receive expected values or standard answers. `textbook-answer.ts` reads the stored answer key on the server, judges submissions, and reveals the standard only after submission.

Older content contracts remain runtime compatibility surfaces. `reading.ts` still understands `content.cards` plus `sr_lesson_i18n`; `quiz.ts` still reads relational `sr_questions` and translation overlays; English content actively uses `sr_lesson_i18n`. The database also retains `sr_content_ledger`, old answer/attempt tables, and `html`/`pdf` columns. The current math workflow neither writes nor requires a concept ledger, neutral card tree, locale overlay, or relational question deck. These surfaces remain so historical content and sibling content types continue to work; they are not alternate authoring paths for new math lessons.

The toolchain has several external relationships. Poppler renders PDF pages, Pillow and SciPy support image and connected-component operations, KaTeX is both formula validator and fragment renderer, potrace plus resvg verify faithful source tracing, JSXGraph plus Playwright render and inspect exact modern diagrams, and Azure `gpt-image-2` supplies semantic artwork through `n-azure`. Publishers use the PostgreSQL client against the shared Supabase schema.

# constraints

Raw extraction and modern edition data must stay separate. Never modernize `pages`, raw `figures`, raw `lessons`, or the captured book answer file. Never publish raw extraction output or an original scan crop as the modern figure. The raw layer is evidence; only a finalized edition is product content.

Lesson identity and mathematical identity are invariant across adaptation. Card id, chapter/section context, printed unit number, exercise order and count, grouping, formula signatures, figure ids, and figure references cannot drift. Contextual number changes require exact declarations. Complete numbered subparts must be normalized into ascending one-per-line order.

TOC assignment is mandatory for product reachability. Page extraction may extend beyond a requested unit to close a cross-page object, but publication must name only complete target lessons. A dry run, an incomplete trailing unit, a failed audit, or a missing card id is not a delivery endpoint.

Modern figures must use the canonical FigureSpec contract. Exact mathematics belongs in deterministic objects and assertions, not in image-model pixels. Hybrid artwork stays below the overlay and preserves intrinsic aspect ratio. Figure labels are English, answer-bearing annotations are forbidden, and generated output requires recorded source references and generation metadata. Renderer output is generated material and must not be hand-edited.

Answer secrecy crosses every boundary. Figure generation may not read answer keys. Browser projections may expose grading mode, labels, units, grid domains, and point names, but never `expected` values or `displayAnswer`. Automatic correctness is judged server-side. Re-publication must preserve existing answer keys, and interaction publication must preserve both answer keys and lesson/figure fields.

Every database merge must target the same edition and exercise identity. The answer publisher rejects a lesson whose stored deck has another edition. Both answer and interaction stages require one item per exercise in the same order. The initial lesson upsert is idempotent by card id; later stages merge into that row rather than creating parallel tables.

Content operations are intended to use `LEMMADECK_DATABASE_URL` for the shared Supabase `lemmadeck-schema`. The publisher code still recognizes older fallback environment names for compatibility, but using those fallbacks for a content write violates the repository's operational boundary and can write to the wrong database.

# known-limits

Scan transcription is not fully automatic. A model must inspect each high-resolution page, identify semantic objects, transcribe text, estimate figure boxes, and mark continuations. Deterministic checks catch many omissions and inconsistencies but cannot prove that every glyph or diagram was interpreted correctly; visual review remains necessary.

Several gates are deliberately semantic. Object counts and schema checks cannot establish that a modern explanation preserves instructional meaning, that distractors or standard answers are mathematically good, or that generated artwork serves the exercise. The lesson, figure, and answer workflows therefore retain human/model review stages even when every mechanical validator passes.

Interaction authoring is incomplete. The pipeline can derive number, math, free, grid-point, and grid-plot behavior, but choice-one and choice-many are reserved rather than mechanically generated. Exact-answer exercises therefore often keep the generic math input and carry `needsAuthoring` until an explicit choice contract is designed and consumed by the application.

The edition validator retains a transitional path for an older `ld-s10y-lesson/figure-spec@1` SVG contract. New figure work should use `ld-s10y-image/figure-spec@1`; legacy migration only produces a draft spec with structural object-count assertions and still requires semantic assertions and visual approval.

The lesson publisher derives `stage` from the card id and uses the printed unit number as `lesson_order`. Because the database enforces uniqueness on `(subject, stage, lesson_order)`, two mathematics volumes for the same grade can collide even when their card ids differ. The publisher surfaces that database conflict rather than silently selecting a different order.

Offline self-contained HTML is a review artifact, not the application source. The current publisher clears the legacy `html` cache on update and does not publish the rendered document; new rows also do not gain a PDF through this path. Existing `pdf` values and legacy schema columns remain outside the current card-fragment contract.

# notes-for-ai

Start any new math lesson request at `.claude/skills/ld-s10y-lesson/SKILL.md`. Resolve the TOC unit before choosing pages, and follow the page-to-assembly-to-edition sequence. Do not revive removed math generators, concept ledgers, neutral card trees, locale overlays, or generic lesson savers as shortcuts.

When changing extraction behavior, inspect the page block parser, line accounting, continuation merge, figure ownership, and TOC assignment together. A local parser change can alter cross-page assembly or cause a card to lose its product id. Verify with the lesson Python tests and the HTML-fragment test, then run the relevant command on representative scan artifacts.

When changing edition rules, compare raw snapshots and modern documents. Preserve identity fields, formula signatures, exercise order, and figure references. A cultural rewrite that changes a number needs a declared numeric change; a layout-only reorder must still preserve formulas and non-math values.

Load `ld-s10y-image` for every modern figure change. Build context from the edition, choose the least generative valid mode, encode exact relationships as assertions, and inspect both the render report and the image at normal application width. Treat legacy SVG migration as a starting draft, not as evidence that the mathematics is correct.

For answer work, solve against the modern edition and inspect every referenced figure. Keep printed answers as `bookRaw` evidence, correct them when necessary, and use `ungraded` when automatic comparison would invent false certainty. Generate and validate interactions only after answer keys are complete.

Before republishing a lesson, account for the merge order: base lesson first, answer keys second, interactions third. Confirm that republishing the base preserves existing answer keys and interactions by exercise number, and ensure later publishers see the same edition. Never hand-write an `sr_lessons` row.

After changes, verify the actual `/card/:id` path. Check catalog availability, prose and exercise fragments, shared-figure placement, desktop and mobile rendering, input widget selection, server-side answer behavior, and absence of expected answers in the initial payload. Keep legacy `reading.ts`, `quiz.ts`, `sr_lesson_i18n`, `sr_content_ledger`, and related schema surfaces unless a separate migration ticket proves that every historical and sibling consumer has been removed.
